 1. SCOPE OF THIS PORTION
-------------------------------------------------------------------------------

 This branch keeps only the parts of the database that belong to:
   - the Service Management API: create, update, list, open/close and delete
     visit types, with validation of required fields, field types and length
     limits
   - the Admin Dashboard statistics endpoint: today's served, no-show and
     cancelled counts, and the average wait, per visit type
   - the rule-based wait-time estimate (people waiting x expected visit
     length, shown as a range up to 30% longer)

 Accounts, profiles, notifications, the patient and front-desk queue
 endpoints and per-patient visit history belong to teammates and are not on
 this branch. The queue table stays because service management reads the
 line (waiting count, someone being called, wait estimate, the capacity and
 delete rules) and the statistics read the visits that left it.

 Endpoints (unchanged from docs/A3-api-spec.txt):
   GET    /services             list, each with waiting, hasCalled, estimatedWait
   GET    /services/:id         one visit type
   POST   /services             create (admin)
   PATCH  /services/:id         update (admin)
   PATCH  /services/:id/open    open or close the line (admin)
   DELETE /services/:id         delete once the line is empty (admin)
   GET    /stats?date=          per visit type for one day, default today (admin)


-------------------------------------------------------------------------------
 2. TABLES AND THE A4 REQUIREMENTS
-------------------------------------------------------------------------------

 A4 requirement   Table          Fields (A4 name -> column)
 ---------------  -------------  ------------------------------------------
 3. Service       services       Service ID -> id, name, description,
                                 Expected duration -> expectedDuration,
                                 Priority level -> priority ('low' |
                                 'medium' | 'high'), capacity
 4. Queue         queues         Queue ID -> id, Service ID -> serviceId,
                                 Status -> status ('open' | 'closed'),
                                 Created date -> createdAt
 5. QueueEntry    queue_entries  Queue ID -> queueId, Position -> position,
                                 Join time -> joinedAt, Status -> status
                                 ('waiting' | 'called' | 'served' |
                                 'no-show' | 'canceled' | 'removed'), plus
                                 priority, calledAt, leftAt
 6. History       visit_history  One row per finished visit: entryId,
                                 serviceId, serviceName, date, joinedAt,
                                 calledAt, leftAt, outcome ('seen' |
                                 'no-show' | 'cancelled' | 'removed')

 Notes on the design
 - Each service has exactly one queue (UNIQUE serviceId), made by a trigger
   when the service is inserted. The API's isOpen is the queue's status.
 - Queue entries are not deleted when a visit ends. The status records how
   it ended and leftAt records when.
 - Wait for the statistics = calledAt - joinedAt of each 'seen' visit.
 - Times the app shows are BIGINT milliseconds since 1970, the numbers the
   API already returned in A3. Calendar dates are DATE, in UTC.


-------------------------------------------------------------------------------
 3. RELATIONSHIPS
-------------------------------------------------------------------------------

   services 1 ---- 1 queues 1 ----< queue_entries
      (serviceId UNIQUE)               |
                                       | trigger T7 copies each finished
                                       v visit (no foreign key)
                                 visit_history

   Deleting a service deletes its queue and that queue's entries (CASCADE),
   but only once nobody is in line (trigger T3). visit_history keeps a copy
   of the service name and has no foreign key, so a day's numbers survive a
   deleted visit type.


-------------------------------------------------------------------------------
 4. SQL TO CREATE THE TABLES
-------------------------------------------------------------------------------

 The exact statements are in server/src/database/schema.sql (tables) and
 server/src/database/triggers.sql (triggers), both run by `npm run
 db:migrate`.

 Table          PK  FK                          Other keys
 -------------  --  --------------------------  ------------------------------
 services       id  -                           UNIQUE name
 queues         id  serviceId -> services.id    UNIQUE serviceId
 queue_entries  id  queueId -> queues.id        UNIQUE calledQueueId,
                                                INDEX (queueId, status,
                                                position)
 visit_history  id  -                           UNIQUE entryId,
                                                INDEX (date, serviceId)

 queue_entries.calledQueueId is a generated column, filled only while the
 entry is being called. Its UNIQUE key lets the database itself guarantee one
 called patient per queue even if two requests arrive at the same moment.


-------------------------------------------------------------------------------
 5. TRIGGERS: WHAT THE DATABASE DOES WHEN A ROW CHANGES
-------------------------------------------------------------------------------

 The service layer checks the same rules first and answers with a clear
 message. The triggers are the guarantee: they hold for every writer (the
 API, the scripts, Workbench, a request that races past the service's own
 check).

 A trigger that refuses a change raises SQLSTATE 45000 with the message
 "<code>|<text>". The API answers it as 409 { error: <code>, message: <text> },
 the same body the service layer sends for that rule
 (server/src/database/signals.js, server/src/api/middleware/errors.js).

 Trigger                     When                  What it does
 --------------------------  --------------------  ----------------------------
 T1 trg_services_after_      a service is added    creates its queue, open
    insert
 T2 trg_services_before_     a service changes     refuses an id change
    update                                         (id-locked) and a capacity
                                                   below the number waiting
                                                   (capacity-below-waiting)
 T3 trg_services_before_     a service is deleted  refuses while anyone is
    delete                                         waiting or called
                                                   (patients-in-line)
 T4 trg_queues_before_       a queue changes       refuses moving it to another
    update                                         service (queue-locked)
 T5 trg_entries_before_      someone joins a line  refuses a closed line
    insert                                         (closed), a full line
                                                   (full), an entry that starts
                                                   finished (not-in-line);
                                                   fills the next position and
                                                   the arrival time if left out
 T6 trg_entries_before_      an entry changes      a finished visit is final
    update                                         (visit-finished); only the
                                                   called patient can be seen
                                                   or a no-show (not-called);
                                                   no leaving before joining
                                                   (bad-time); no moving lines
                                                   (entry-locked); stamps
                                                   calledAt and leftAt if left
                                                   out
 T7 trg_entries_after_       an entry leaves the   writes its visit_history
    update                   line                  row: served -> seen,
                                                   canceled -> cancelled,
                                                   no-show, removed
 T8 trg_history_before_      history changes       refuses: history is a
    update                                         record (history-locked)

 Allowed moves through a line (T6):
   waiting -> called -> served | no-show
   waiting | called -> canceled | removed
   called -> waiting (sent back; calledAt is cleared)

 Note for hosted MySQL (e.g. Aiven): with binary logging on, a user without
 SUPER can only create triggers when the server setting
 log_bin_trust_function_creators is on. `npm run db:migrate` says so if
 that is the problem.


-------------------------------------------------------------------------------
 6. VALIDATION: BACKEND AND DATABASE
-------------------------------------------------------------------------------

 The backend checks every request first (server/src/api/validation/), and the
 database rejects anything that still gets through.

 Rule              Backend (400 with field messages)   Database
 ----------------  ----------------------------------  ------------------------
 Required fields   schemas.js "required"               NOT NULL, CHECK
                                                       CHAR_LENGTH(TRIM(...))
 Length limits     name 3-100, description <= 300      VARCHAR(n), CHECK >= 3
 Data types        checkType (string/integer/boolean)  INT, BIGINT, DATE, ENUM
 Allowed values    oneOf (priority low/medium/high)    ENUM columns
 Ranges            duration 1-120, capacity 1-50       CHECK BETWEEN
 Unique values     service checks (409 name-taken)     UNIQUE name, one called
                                                       patient per queue
 Relationships     service checks (404)                FOREIGN KEY
 Business rules    servicesService.js (409)            triggers T2-T8

 If the database rejects a value, the API still answers in its usual shape:
 a trigger refusal becomes 409 with the rule's code, a broken UNIQUE key 409
 "conflict", and a broken CHECK, length, type or NOT NULL rule 400
 "validation".


-------------------------------------------------------------------------------
 7. HOW THE BACKEND USES THE DATABASE
-------------------------------------------------------------------------------

   screens -> src/api -> (HTTP) -> routes -> controllers -> services
     -> repositories (SQL) -> mysql.js (connection pool) -> MySQL (+ triggers)

 server/src/database/
   mysql.js         connection pool from DATABASE_URL, query(), queryOne(),
                    transaction()
   schema.sql       CREATE TABLE statements
   triggers.sql     the triggers in section 5
   sqlFile.js       reads .sql files, including DELIMITER, like the mysql
                    client does
   setup.js         create/drop tables and triggers, row counts
   signals.js       reads a trigger's "<code>|<text>" refusal
   seed.js          the five sample visit types; in-memory rows for the tests
   mock/activity.js the mock-data engine (section 8)
   dumpSql.js       builds and reads a dump
   migrate.js, populate.js, live.js, dump.js   the npm scripts
   repositories/    every SQL query in the app: servicesRepo, queueRepo,
                    historyRepo

 A service created closed is inserted and closed in one transaction, so
 nobody can check in between. Queries use placeholders (?), so values are
 never pasted into the SQL text.

 8. SAMPLE DATA: EMPTY DATABASE, POPULATE, LIVE, DUMP
-------------------------------------------------------------------------------

 The database starts empty and fills up as you go.

   npm run db:migrate   creates the tables and triggers; keeps data
   npm run db:reset     DELETES these tables and their data, then creates
                        them again, empty
   npm run db:populate  adds sample data on top of what is there:
                          - the five sample visit types, if missing
                            (Prescription Refill closed)
                          - per open line, 3-6 visits that already ended
                            today (seen, no-show, cancelled, removed) and
                            1-4 patients still waiting
                        All times are relative to now, so "today" on the
                        admin dashboard always has numbers. Run it again to
                        add more. `-- --seed 42` repeats a run.
   npm run db:live      keeps the database moving: every few seconds a
                        patient checks in, is called, is seen or a no-show,
                        or cancels, stamped with the current time. Prints
                        each event and the day's statistics. Ctrl+C stops.
                        `-- --every 3 --ticks 50 --seed 7`
   npm run db:dump      writes the whole database to
                        server/src/database/dump.sql (or `-- file.sql`)
   npm run db:load      replaces the tables with that dump (or `-- file.sql`)

 Every sample visit goes through the real line (join -> call -> finish), so
 the triggers check each step and write the history the statistics read.
 Steps the database refuses (a closed or full line) are printed as
 "refused by the database", because refusing them is the point.

 The dump lists DROP TABLE, CREATE TABLE, the rows, and then the triggers,
 as mysqldump does, so loading it does not run the triggers a second time.
 It also loads with `mysql -h HOST -P PORT -u USER -p DB < dump.sql` and
 in Workbench. The committed dump.sql was made from an empty database with
 `db:reset`, `db:populate -- --seed 42` and 20 `db:live` events, so its
 dates are the day it was made; use db:populate for data dated today.

 9. TESTS AND COVERAGE
-------------------------------------------------------------------------------

   npm test               every unit and API test; no database needed. The
                          services run on in-memory stand-ins
                          (server/tests/fakes/). The stand-in line copies the
                          triggers, so the mock-data engine is tested too.
   npm run test:coverage  the same, with the coverage report
                          (server/coverage/index.html). Fails below 75%.
   npm run test:mysql     the real repositories and every trigger against
                          DATABASE_URL. Only touches visit types it creates
                          and deletes them.

   tests/unit/servicesService.test.js   service management rules
   tests/unit/historyStats.test.js      statistics
   tests/unit/waitEstimate.test.js      wait-time estimate
   tests/unit/validation.test.js        required fields, types, lengths
   tests/unit/repositories.test.js      each SQL repository
   tests/unit/databaseSetup.test.js     schema, triggers, .sql reading
   tests/unit/dump.test.js              dump builder
   tests/unit/mockActivity.test.js      populate and live
   tests/unit/errorHandler.test.js      trigger refusal -> 409
   tests/integration/api.test.js        the endpoints over HTTP
   tests/mysql/repositories.test.js     triggers and repositories on MySQL

 Result when this was written: 130 tests passed with 99.7% line coverage
 (npm run test:coverage), and 24 of 24 MySQL tests passed on MySQL 8.4.


-------------------------------------------------------------------------------
 10. RUNNING IT
-------------------------------------------------------------------------------

 This branch drops and rebuilds its own tables, so give it a database of its
 own, not the team's shared one. With Docker Desktop:

   cd server
   copy .env.example .env        (DATABASE_URL points at the local MySQL)
   npm ci
   npm run db:up                 starts MySQL 8.4 (docker-compose.yml)
   npm run db:migrate            empty tables + triggers
   npm run db:populate           sample data for today
   npm run dev                   API on http://localhost:4000
   npm run db:live               (second terminal) live activity

 Sign-in is not on this branch. `npm run token` prints an admin bearer token
 for curl or Postman:
   curl -H "Authorization: Bearer <token>" http://localhost:4000/stats
