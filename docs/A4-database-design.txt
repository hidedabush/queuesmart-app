 1. CHOICE OF DATABASE
-------------------------------------------------------------------------------

 MySQL, a relational database. The A1 container diagram already showed a
 "Database [SQL]" box, and the data is strongly related: entries belong to
 a queue, a queue to a service, and every entry, notification and visit to a
 user. Foreign keys, UNIQUE keys and transactions enforce those rules in the
 database itself.

 Each teammate runs MySQL 8.4 on their own laptop, free: in Docker
 (server/docker-compose.yml, started by `npm run db:start`) or installed by
 hand (SETUP.md). The server finds it through DATABASE_URL in server/.env.

 2. TABLES AND THE A4 REQUIREMENTS
-------------------------------------------------------------------------------

 A4 requirement      Table              Fields (A4 name -> column)
 ------------------  -----------------  ----------------------------------------
 1. UserCredentials  user_credentials   User ID -> id, Email -> email,
                                        Encrypted password -> passwordHash
                                        (scrypt, salted), Role -> role
                                        ('user' | 'admin')
 2. UserProfile      user_profiles      Full name -> fullName, Email -> email
                                        (FK to user_credentials.email),
                                        Contact -> phone, Preferences ->
                                        preferences (JSON), plus dob
 3. Service          services           Service ID -> id, name, description,
                                        Expected duration -> expectedDuration,
                                        Priority level -> priority, capacity
 4. Queue            queues             Queue ID -> id, Service ID ->
                                        serviceId, Status -> status
                                        ('open' | 'closed'), Created date ->
                                        createdAt
 5. QueueEntry       queue_entries      Queue ID -> queueId, User ID ->
                                        userId, Position -> position, Join
                                        time -> joinedAt, Status -> status
                                        ('waiting' | 'called' | 'served' |
                                        'no-show' | 'canceled' | 'removed')
 6. Notification     notifications      User ID -> userId, Message -> title +
                                        message, Timestamp -> createdAt,
                                        Status -> status ('sent' | 'viewed'),
                                        plus type, entryId, serviceId and
                                        channels from docs/A3-api-spec.txt
                                        section 6
 6. History          visit_history      One row per finished visit: userId,
                                        service, date, times, outcome

 Notes on the design
 - Passwords are never stored. passwordHash holds "salt:hash" from scrypt
   (a one-way, salted hash). NULL means the account cannot sign in; these
   are patients registered at the front desk.
 - Each service has exactly one queue (UNIQUE serviceId). The API still
   shows a service's isOpen; it reads the queue's status.
 - Queue entries are not deleted when a patient leaves. The status records
   how the visit ended and leftAt records when, so the queue keeps a full
   record of the day.
 - position is the arrival order within a queue. Urgent patients are served
   first, so the place shown to the patient is worked out from priority and
   position.
 - Times the app shows are BIGINT milliseconds since 1970, the numbers the
   API already returned in A3. Calendar dates use DATE.


-------------------------------------------------------------------------------
 3. RELATIONSHIPS
-------------------------------------------------------------------------------

   user_credentials 1 ---- 1 user_profiles        (email, ON UPDATE CASCADE)
          |
          | 1
          +---------------< queue_entries >--------------+
          |                       | n                    |
          +----< notifications    |                      |
          |                       | 1                    |
          +----< visit_history  queues 1 ---- 1 services
                                (serviceId UNIQUE)

   Deleting a service deletes its queue and that queue's entries (CASCADE).
   Visit history keeps a copy of the service name and has no foreign key to
   services, so a patient's history survives a deleted visit type.


-------------------------------------------------------------------------------
 4. SQL TO CREATE THE TABLES
-------------------------------------------------------------------------------

 The exact statements are in server/src/database/schema.sql (run by
 `npm run db:migrate`). Primary keys (PK), foreign keys (FK) and other keys:

 Table             PK      FK                                      Other keys
 ----------------  ------  --------------------------------------  ----------------------------
 user_credentials  id      -                                       UNIQUE email
 user_profiles     email   email -> user_credentials.email         -
 services          id      -                                       UNIQUE name
 queues            id      serviceId -> services.id                UNIQUE serviceId
 queue_entries     id      queueId -> queues.id,                   UNIQUE activeUserId,
                           userId -> user_credentials.id           UNIQUE calledQueueId
 notifications     id      userId -> user_credentials.id,          INDEX (userId, createdAt),
                           entryId -> queue_entries.id             INDEX (entryId, type)
 visit_history     id      userId -> user_credentials.id           INDEX (userId, leftAt),
                                                                   INDEX (date)

 queue_entries has two generated columns that are filled only while the
 patient is still in line. Their UNIQUE keys let the database itself
 guarantee two rules even if two requests arrive at the same moment:
   activeUserId   one active check-in per patient
   calledQueueId  one called patient per queue


-------------------------------------------------------------------------------
 5. NOTIFICATIONS IN THE DATABASE
-------------------------------------------------------------------------------

 The endpoints, notification shape and message templates are the ones in
 docs/A3-api-spec.txt section 6 (the notification component in
 server/src/api/notifications/). A4 stores them in the notifications table:

   GET   /notifications/me           { notifications, unread }, newest first
   PATCH /notifications/:id/read     { notification }, 404 if not the caller's
   POST  /notifications/me/read-all  { unread: 0 }  ("Clear all")

 The API's read flag is stored as A4's status column: read = false is
 'sent', read = true is 'viewed'. channels is stored as JSON.

 When notices are made (the spec's "Triggers"):
   joined     the patient checks in
   almost-up  the line changes (check-in, cancel, call, move, remove) and
              the patient has 2 or fewer ahead; once per check-in
   called     the front desk calls the patient
 When the patient leaves the line, every unread notice for that check-in is
 marked read. Notifications never include the reason for the visit, because
 they can show on a lock screen. The patient dashboard's bell lists the
 unread ones.

 Every other endpoint is unchanged from docs/A3-api-spec.txt.


-------------------------------------------------------------------------------
 6. VALIDATION: BACKEND AND DATABASE
-------------------------------------------------------------------------------

 The backend checks every request first (server/src/api/validation/), and the
 database rejects anything that still gets through.

 Rule               Backend (400 with field messages)  Database
 -----------------  ---------------------------------  -------------------------
 Required fields    schemas.js "required"              NOT NULL
 Length limits      length / maxLength rules           VARCHAR(n), CHECK
                                                        CHAR_LENGTH(...) >= 3
 Data types         checkType (string/integer/...)     INT, BIGINT, DATE, ENUM,
                                                        JSON
 Allowed values     oneOf (priority, outcome, ...)     ENUM columns
 Ranges             intRange (duration 1-120,          CHECK BETWEEN
                    capacity 1-50)
 Formats            email and phone patterns           CHECK (email LIKE, phone
                                                        REGEXP '^[0-9]{10}$')
 Unique values      service checks (409)               UNIQUE email, service
                                                        name, active check-in,
                                                        called patient
 Relationships      service checks (404)               FOREIGN KEY
 Business rules     services (409: full, closed,       triggers (section 10)
                    capacity-below-waiting, ...)

 If the database rejects a value, the API still answers in its usual shape:
 a trigger's refusal becomes 409 with the rule's own code (the same body the
 service sends), a broken UNIQUE key becomes 409 "conflict", and a broken
 CHECK, length, type or NOT NULL rule becomes 400 "validation"
 (server/src/api/middleware/errors.js).

 7. HOW THE BACKEND USES THE DATABASE
-------------------------------------------------------------------------------

   screens -> src/api -> (HTTP) -> routes -> controllers -> services
     -> repositories (SQL) -> mysql.js (connection pool) -> MySQL

 server/src/database/
   mysql.js         connection pool from DATABASE_URL,
                    query(), queryOne(), transaction()
   schema.sql       CREATE TABLE statements
   triggers.sql     the triggers in section 10
   sqlFile.js       reads .sql files, including DELIMITER, like the mysql
                    client does
   signals.js       reads a trigger's "<code>|<text>" refusal
   setup.js         create/drop tables and triggers, load data
   migrate.js       npm run db:migrate | db:seed | db:reset | db:empty |
                    db:load
   seed.js          demo data
   mock/activity.js, populate.js, live.js, dumpSql.js, dump.js
                    sample data and the dump (section 11)
   repositories/    every SQL query in the app: userRepo, servicesRepo,
                    queueRepo, historyRepo, notificationRepo

 Writes that touch two tables run in one transaction: a new user (credentials
 + profile), a new service (the service; trigger T1 adds its queue, and a
 service created closed is closed in the same transaction), and loading demo
 data.

 Queries use placeholders (?), so values are never pasted into the SQL text.

 10. TRIGGERS: WHAT THE DATABASE DOES WHEN A ROW CHANGES
-------------------------------------------------------------------------------

 server/src/database/triggers.sql, run by `npm run db:migrate` after
 schema.sql. The services check the same rules first and answer with a clear
 message; the triggers make the rules hold for every writer (the API, the
 scripts, Workbench, or two requests that race past the service's check).
 They never write rows the API writes itself: the history module records
 visit_history and the notification module records notifications.

 A trigger that refuses a change raises SQLSTATE 45000 with the message
 "<code>|<text>". The API answers 409 { error: <code>, message: <text> }, the
 same body the service sends for that rule (server/src/database/signals.js,
 server/src/api/middleware/errors.js).

 Trigger                        When                  What it does
 -----------------------------  --------------------  --------------------------
 T1 trg_services_after_insert   a service is added    creates its queue, open
                                                      (queue-<service id>)
 T2 trg_services_before_update  a service changes     refuses an id change
                                                      (id-locked) and a capacity
                                                      below the number waiting
                                                      (capacity-below-waiting)
 T3 trg_services_before_delete  a service is deleted  refuses while anyone is
                                                      waiting or called
                                                      (patients-in-line)
 T4 trg_queues_before_update    a queue changes       refuses moving it to
                                                      another service
                                                      (queue-locked)
 T5 trg_entries_before_insert   someone joins a line  refuses a closed line
                                                      (closed) and a full one:
                                                      waiting + called at
                                                      capacity, as joinQueue
                                                      counts (full). Finished
                                                      rows (demo data, a dump)
                                                      are records and pass.
 T6 trg_entries_before_update   an entry changes      a finished visit is final
                                                      (visit-finished); only the
                                                      called patient can be seen
                                                      or a no-show (not-called);
                                                      no leaving before joining
                                                      (bad-time); no moving to
                                                      another line or patient
                                                      (entry-locked). Stamps
                                                      calledAt / leftAt if a
                                                      writer leaves them out.
 T7 trg_history_before_update   history changes       refuses: history is a
                                                      record (history-locked)

 MySQL with binary logging on (the default): a user without SUPER can
 only create triggers when the server setting log_bin_trust_function_creators
 is on. `npm run db:migrate` says so if that is the problem.

 11. SAMPLE DATA: EMPTY DATABASE, POPULATE, LIVE, DUMP
-------------------------------------------------------------------------------

   npm run db:empty     DELETES every table and all data, then creates them
                        again, empty (db:reset does the same and reseeds)
   npm run db:populate  adds sample data on top of what is there:
                          - an empty database first gets the demo data
                            (db:seed: demo accounts, 5 visit types, people
                            waiting, a finished morning)
                          - then, on every open line, 3-6 visits that already
                            ended today (new front-desk patients, their
                            finished entry, history row and read notices)
                          - and 1-3 patients checking in now, through the
                            app's own check-in (queueService.joinQueue)
                        All times are relative to now, so "today" on the
                        admin dashboard always has numbers. Run it again to
                        add more. `-- --seed 42` repeats a run.
   npm run db:live      keeps the office moving: every few seconds a patient
                        checks in, is called, is seen or a no-show, or
                        cancels, through queueService and staffQueueService,
                        so history and notifications are written as for a
                        real patient. Prints each event and the day's
                        statistics. Ctrl+C stops.
                        `-- --every 3 --ticks 50 --seed 7`
   npm run db:dump      writes every table to server/src/database/dump.sql
                        (or `-- file.sql`); no mysqldump needed
   npm run db:load      REPLACES every table with that dump (or `-- file.sql`)
   npm run db:start     starts MySQL 8.4 in Docker (server/docker-compose.yml),
                        creates the tables and adds the demo data if empty

 A step that is refused (a closed or full line) is printed, not thrown,
 because refusing it is the point.

 The dump lists DROP TABLE, CREATE TABLE, the rows, and then the triggers, as
 mysqldump does, so loading it does not run the triggers on the rows. It also
 loads with `mysql -h HOST -P PORT -u USER -p DB < dump.sql` and in
 Workbench. The committed dump.sql was made from an empty database with
 db:empty, db:populate (seeds 42 and 43) and 30 db:live events, so its dates
 are the day it was made; use db:populate for data dated today.
