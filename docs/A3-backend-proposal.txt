 0. SUMMARY
-------------------------------------------------------------------------------

 We build the backend as a standalone Node + Express server in a new
 server/ folder. It exposes the REST API the A2 code already outlines in the
 route comments in src/api/*.js. The Expo app stops calling business logic
 directly and sends HTTP requests to the server.

 The design follows the two A1 diagrams box for box:

   Mobile Application  -->  QueueSmart Backend  -->  Database [SQL]
                            (Back-end/API +           (A3: in-memory stand-in)
                             Notification component)
                                     |
                                     +-->  SMS [external]  (A3: mock gateway)

 There is no real database or real SMS in A3. Both sit behind interfaces
 (repositories and SmsGateway), so in A4 we rewrite only those files and
 leave the API, the business rules and the screens alone.

 D. DATA MODEL  (exactly the four tables in the A1 Database box)

   +----------------------+              +------------------------------+
   | users                |              | services                     |
   +----------------------+              +------------------------------+
   | id            PK     |              | id               PK          |
   | name                 |              | name             UNIQUE      |
   | dob    (YYYY-MM-DD)  |              | description                  |
   | email         UNIQUE |              | expectedDuration (minutes)   |
   | phone    (nullable)  |              | priority  low|medium|high    |
   | passwordHash         |              | capacity  (daily walk-ins)   |
   | salt                 |              | isOpen                       |
   | role    user|admin   |              +------------------------------+
   | createdAt            |                          | 1
   +----------------------+                          |
              | 1                                    |
              |                                      |
              | *                                    | *
   +-----------------------------------------------------------------+
   | queueEntries                                                    |
   +-----------------------------------------------------------------+
   | id PK | userId FK | serviceId FK | reason | status waiting|called|
   | priority normal|urgent | order | arrivedAt | calledAt            |
   +-----------------------------------------------------------------+
              |
              | when an entry leaves a line, one row is written to:
              v
   +-----------------------------------------------------------------+
   | history                                                         |
   +-----------------------------------------------------------------+
   | id PK | userId FK | serviceId | serviceName | date              |
   | joinedAt | leftAt | outcome seen|no-show|cancelled|removed      |
   +-----------------------------------------------------------------+

   Notes
   - serviceName is copied into history so past visits still read correctly
     after a visit type is renamed or deleted.
   - Sessions are not a table. Login returns a signed token
     (userId.role.expiry.HMAC-signature, Node's built-in crypto), so the
     server verifies it without a lookup and the Database box keeps exactly
     its four A1 tables.
   - The notification outbox belongs to the Notification component (see
     rules under diagram B).
   - "waiting" and "hasCalled" on a service are computed from queueEntries on
     every read and never stored, so they cannot drift (same as A2).

-------------------------------------------------------------------------------
 4. MODULE DESIGNS
-------------------------------------------------------------------------------

 4.1 AUTHENTICATION  (Back-end / API)

   Endpoints        POST /auth/register, POST /auth/login, GET /auth/me
   Passwords        Hashed with crypto.scrypt and a random 16-byte salt,
                    compared with crypto.timingSafeEqual. The server never
                    stores or returns a plain password.
   Tokens           signToken({ userId, role }) -> "id.role.expiry.sig"
                    with an HMAC-SHA256 signature. Expires after 8 hours.
                    verifyToken rejects a bad signature or an expired token.
   Roles            'user' (patient) or 'admin' (front desk).
                    requireAuth     -> 401 with no token or a bad one
                    requireRole('admin') -> 403 when the role is not admin
   Admin sign-in    admin-login.js calls the same /auth/login and refuses
                    the result unless user.role === 'admin'. The server also
                    enforces this on every staff route.
   Registration     Creates role 'user' only. Admin accounts come from the
                    seed (admin@queuesmart.test), so nobody can register
                    as staff.
   Validation       Same rules the A2 screens use (see A3-api-spec.txt):
                    name (two words), DOB (MM/DD/YYYY, real date, age 0-120),
                    email format, strong password, optional 10-digit phone.


 4.2 SERVICE MANAGEMENT  (Back-end / API, admin writes)

   Endpoints        GET  /services              any signed-in user
                    GET  /services/:id          any signed-in user
                    POST /services              admin
                    PATCH /services/:id         admin
                    PATCH /services/:id/open    admin
                    DELETE /services/:id        admin
   Required fields  name, description, expectedDuration, priority (the four
                    the brief lists), plus capacity (office rule #4).
   Business rules   - names are unique, ignoring case
                    - capacity can't drop below the number waiting
                    - closing stops new check-ins only (rule #9)
                    - delete is blocked while anyone is in line (rule #10)
   Response extras  waiting, hasCalled and estimatedWait, computed on read.


 4.3 QUEUE MANAGEMENT  (Back-end / API)

   Patient          POST   /services/:id/queue     join  { reason }
                    DELETE /queue/me               leave
                    GET    /queue/me               my place, status, wait
   Admin            GET    /services/:id/queue     view current line
                    POST   /services/:id/queue/call    serve next
                    POST   /services/:id/queue/called  { outcome }
                    PATCH  /queue/:entryId         { direction } or { priority }
                    DELETE /queue/:entryId         remove from line

   Ordering - arrival order plus priority (brief: "Queue ordering should
   consider arrival order and priority"):

     Each line already belongs to one visit type, so the visit type's
     priority can't order patients within its own line. Priority is
     therefore stored on each queue entry:

        entry.priority = 'normal' (default) | 'urgent' (set by staff triage)

     The line is sorted by

        1. priority rank, urgent before normal
        2. order ASC   (arrival sequence; staff can swap within one level)

     Example, Sick Visit line:
        arrival:  Maria(1) James(2) Aisha(3) Daniel(4)
        staff triage Daniel -> urgent
        line:     Daniel(4,U) Maria(1) James(2) Aisha(3)

   Entry lifecycle:

        join
          |
          v
     +-----------+  callNext (only one called per line)  +----------+
     |  waiting  | ------------------------------------> |  called  |
     +-----------+                                       +----------+
       |   ^   |                                          |        |
       |   |   +-- triage / move: re-sorted, stays waiting|        |
       |   +-------------------------------------------+  |        |
       |                                                  | seen   | no-show
       | leave (patient)  -> history: cancelled           v        v
       | remove (staff)   -> history: removed       history: seen / no-show
       |                     (from either state)

     Every transition also calls notifications.trigger(...)
     (the "Alerts triggers" arrow).

   Unchanged A2 rules: checkInBlocker (missing / already-checked-in /
   closed / full), reason 3-120 chars, one check-in per patient, one called
   patient per line. The isCurrentUser flag is replaced by req.user.id from
   the token.


 4.4 WAIT-TIME ESTIMATION  (Back-end / API)

   Rule-based, as in A1 and allowed by the brief:

       low  = peopleAhead x service.expectedDuration
       high = round(low x 1.3)
       shown as "low-high min"

   - Per service (joining now):   peopleAhead = waiting count
   - Per patient (GET /queue/me): peopleAhead = index in the sorted line
   - Closed or empty line: estimatedWait = null ("No wait" / "Closed")
   The server computes it on every response. The phone only formats it.


 4.5 NOTIFICATIONS  ("Notification component" -> "SMS [external]")

   The API reports what happened. The component decides who gets alerted
   and when.

   API event                    Decision (who / when)                 Delivery
   ---------------------------  ------------------------------------  -----------------
   queue.joined(entry)          the joiner, immediately ("joined")    outbox + SMS mock
   queue.changed(serviceId)     every waiting entry whose             outbox + SMS mock
     after call / leave /       peopleAhead <= HEAD_IN_AHEAD (2):
     remove / move / triage     "almost-up", once per entry
   queue.called(entry)          the called patient: "called"          outbox + SMS mock
                                ("notify when the service is ready")

   Rules
   - Duplicates are skipped, keyed on (entryId, type), so reshuffles don't
     spam the patient.
   - Text never includes the reason for the visit; it can appear on a lock
     screen (office rule #8).
   - SMS goes out only when the user gave a phone number. The in-app outbox
     always gets the message.
   - MockSmsGateway.send(to, text) prints "[SMS -> 555...] text" and keeps a
     sent list (tests read it). In A4 a real provider implements the same
     send().

   Endpoints        GET   /notifications/me
                    PATCH /notifications/:id/read
                    POST  /notifications/me/read-all
   Front end        The bell sheet in src/app/user/dashboard.js reads this
                    list instead of building notifications on the phone.


 4.6 HISTORY  (Back-end / API -> Database.history)

   - historyService.record(entry, outcome) runs on every exit from a line:
     seen, no-show, cancelled or removed.
   - GET /history/me returns the signed-in patient's visits, newest first.
     A patient can never read anyone else's history.
   - Admin statistics (the "view statistics" arrow in A1 #1):
       GET /stats -> per service, for today: served, noShows, cancelled,
                     currentlyWaiting, averageWaitMinutes
     All of it is read from history and queueEntries. Nothing extra is
     stored.

 5. VALIDATION AND ERROR CONTRACT
-------------------------------------------------------------------------------

 Every route with a body runs validate(schema) before its controller. Each
 field is checked in this order:

     1. required        missing, null or blank string        -> error
     2. type            string / integer / boolean / enum    -> error
     3. length / range  minLength, maxLength, intRange       -> error
     4. format          email, date, phone, password rules   -> error

 All failing fields come back together, so the form can show every error
 at once.

 Every error, from any route, has this shape:

     HTTP 400  { "error": "validation",
                 "fields": { "name": "Use 3-60 characters.",
                             "expectedDuration": "Enter a whole number from 1 to 240." } }
     HTTP 401  { "error": "unauthenticated", "message": "..." }
     HTTP 403  { "error": "forbidden",       "message": "..." }
     HTTP 404  { "error": "not-found",       "message": "..." }
     HTTP 409  { "error": "<rule>",          "message": "..." }
               rule = full | closed | already-checked-in | already-calling
                      | empty | nothing-called | patients-in-line
                      | capacity-below-waiting
                      | email-taken | name-taken
     HTTP 500  { "error": "server", "message": "Something went wrong." }

 The 409 codes reuse the strings A2's checkInBlocker and deleteService
 already return, so the screens' existing error messages keep working.

 6. FRONT-END INTEGRATION  ("Send requests to" arrow)
-------------------------------------------------------------------------------

 Layering stays as in the README, with HTTP between api and the server:

   screens -> frontend/state -> src/api -> (HTTP) -> server/

 6.1 src/api/client.js  (new)
     - request(method, path, body) -> parsed JSON
     - Base URL: EXPO_PUBLIC_API_URL if set. Otherwise the laptop's LAN IP
       from Constants.expoConfig.hostUri plus ":4000", because Expo Go on a
       phone can't reach "localhost".
     - Attaches "Authorization: Bearer <token>".
     - On a non-2xx response, throws ApiError { status, error, fields, message }.

 6.2 src/api/*.js
     - services.js and queue.js keep the same function names; their bodies
       become request(...) calls.
     - New: auth.js, notifications.js, history.js, stats.js.

 6.3 src/frontend/state/ServicesStore.js
     - readAll() becomes async; change() awaits the call and then refreshes.
     - Holds { token, user } and exposes useAuth(): login, register, logout.
     - Polls every 5 s while signed in, so a patient sees their place move
       after staff serve the next person on another device.

 6.4 Screens (small edits)
     - Add await wherever an action's result is used, e.g.
       join-queue.js (checkIn) and admin/services/[id].js (create/delete).
     - login.js, register.js and admin-login.js call the auth API. Server
       400 fields are shown under the matching <Field>.
     - The dashboard bell reads GET /notifications/me.
     - The admin dashboard can show GET /stats.

 6.5 Client-side rules
     The rules the screens need for instant feedback (REASON_MAX,
     EMERGENCY_NOTICE, validateReason, displayName, formatWait) are copied
     into src/frontend/rules.js. The server always re-checks and is the
     authority.

 6.6 Clean-up
     src/backend/ and src/database/ are deleted from the app once the
     server owns them, so there is only one source of truth.

 6.7 Running both
     terminal 1:  cd server && npm install && npm run dev   (port 4000)
     terminal 2:  npx expo start
     The phone and the laptop must be on the same Wi-Fi.
